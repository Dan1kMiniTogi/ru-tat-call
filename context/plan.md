# План реализации

Правило: каждый этап даёт **запускаемый** результат. Не начинать с идеальной модели, кастомной видеоплатформы, диаризации или «продакшен UI без связи».

## Этапы

| Этап | Цель | Готово когда |
| --- | --- | --- |
| **0** Проектирование | ТЗ, контракты, стек, каркас репо | Можно кодить без смены концепции |
| **1** Инфра | Signaling + user backend + ASR-заглушка + docker-compose + TLS | Подъём одной командой, тестовый ASR endpoint |
| **2** Flutter shell | Логин, контакты, макет звонка и зоны субтитров | Android/iOS запускаются, UI не знает модель |
| **3** Звонок без ASR | WebRTC + signaling, 2–4 участника | A/V есть, hangup/reconnect |
| **4** Streaming ASR | Реальный поток, любая первая модель | partial/final, сбой ASR не убивает звонок |
| **5** Субтитры в UI | Speaker labels, partial→final, история звонка | Читаемо, без лагов UI |
| **6** Mixed RU/TT | Подбор модели, постобработка, живые диалоги | Без ручного языка |
| **7** Надёжность | Reconnect, нагрузка, UX ошибок | Сбои предсказуемы |
| **8** MVP | Сборка для семейного использования | См. критерии в product.md |
| **9** После MVP | Сначала стабильность и качество ASR, потом latency, читаемость, хранение, поиск, перевод, резюме | Каждая фича выключаема |

Практический порядок: документы → backend skeleton → Flutter shell → звонок → ASR API → субтитры → мультиязычность → тесты → стабилизация → MVP.

## Где мы сейчас

Реализация живёт в `project/` (uv workspace). Этап **0** (каркас) начат: шаг 0.1 готов. Дальше 0.2 — Pydantic-контракты в `project/shared/`.

Ранний ML-spike (голос → текст на готовых wav2vec-tatar) можно делать **рядом** с этапом 4, не блокируя звонок.

## Тесты (сжато)

Порядок: auth → контакты → звонок без ASR → ASR без UI → субтитры → mixed → отказы → нагрузка → длинный живой звонок.

Нагрузка семьи: 2 человека 10–15 мин; 4 человека 20–30 мин; серия коротких звонков на утечки.

Провал MVP: субтитры опаздывают постоянно; звонок сыпется; mixed ломает текст; только одна платформа; обязательный ручной язык; ASR валит приложение; клиент прибит к одной модели; перегруженный UI.
